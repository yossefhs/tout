# 02 — Audit automatique du site d'un prospect (`audit_site.py`)

Composant B de la chaîne de prospection. Prend l'URL d'un site, le consulte en lecture seule, mesure l'affichage mobile et la vitesse, puis produit une liste de constats sourcés, un verdict et un rapport en français prêt à alimenter l'e-mail (composant D) et la maquette (composant C). Rédigé le 2026-11-05.

## Emplacement et usage

- Script : `/home/user/refonte-vitrine/pipeline/scripts/audit_site.py` (Python 3.13, venv `/home/user/.venv-webtest` : requests, beautifulsoup4, lxml, playwright 1.64.1 ; Node 22 pour Lighthouse via `npx`).
- Exécutable directement (shebang vers le venv). Exporter `PLAYWRIGHT_BROWSERS_PATH=/home/user/.venv-webtest/ms-playwright` ; le script le fait lui-même si la variable est absente et que le dossier existe. `CHROME_PATH` est fixé à `/opt/pw-browsers/chromium-1243/chrome-linux64/chrome` pour Lighthouse s'il n'est pas déjà défini.

```bash
export PLAYWRIGHT_BROWSERS_PATH=/home/user/.venv-webtest/ms-playwright
/home/user/refonte-vitrine/pipeline/scripts/audit_site.py https://exemple.fr/ --out /home/user/refonte-vitrine/pipeline/out/exemple-fr
# options
#   --pages 4          pages internes au maximum (0 à 4 ; défaut 4)
#   --ville Chartres   ville attendue (issue du lead) : aide la détection « ville sur l'accueil »
#   --cp 28000         code postal attendu (même usage)
#   --nom "SARL X"     dénomination du lead (SIRENE) : recherchée sur le site (« correspondance_entreprise »)
#   --enseigne "X"     enseigne du lead : même usage
#   --siren 123456789  SIREN du lead : recherché sur le site, SIRET compris
#   --metier "plombier chauffagiste"   libellé du métier : sert aux exemples des corrections (alt des images)
#   --timeout 12       délai HTTP en secondes (connexion + lecture)
#   --no-browser       sans Playwright (ni captures, ni débordement, ni bouton d'appel)
#   --no-lighthouse    sans Lighthouse (scores marqués « non mesuré »)
```

Sortie standard : une ligne JSON de résumé (`url`, `url_finale`, `domaine_demande`, `domaine_final`, `verdict`, `constats`, `gravites`, `lighthouse_performance`, `correspondance_entreprise`, `correspondance_non_trouves`, `duree_s`, `out`, `erreurs`) pour l'enchaînement avec les autres composants ; la progression est sur stderr (`[audit] …`). Code de sortie 0 dès que `audit.json` est écrit, 2 si les arguments sont invalides.

- `domaine_demande` / `domaine_final` : hôte de l'URL demandée et de l'URL finale après redirections, sans `www.` ni port (ex. `grouperoyenergie.com` → `gre-enr.fr`) ; `cible.hote_final` garde l'hôte complet. Le registre peut ainsi tenir les deux domaines (règle « jamais deux e-mails au même domaine »). `domaine_final` est `null` si l'accueil n'a pas répondu.
- `correspondance_entreprise` : liste des éléments du lead retrouvés sur les pages consultées parmi `nom`, `enseigne`, `ville`, `cp`, `siren` (fournis par `--nom`, `--enseigne`, `--ville`, `--cp`, `--siren`) ; `correspondance_non_trouves` liste ceux fournis mais absents. Le détail (page où l'élément a été vu, mode de reconnaissance) est dans `analyse.correspondance_entreprise`. Nom et enseigne sont reconnus sans casse ni accents, soit par le libellé entier, soit quand tous leurs mots significatifs (forme juridique et mots-outils exclus) figurent sur une même page ; le SIREN est cherché dans les suites de chiffres (SIRET compris). Le runbook peut décider « site relié à l'entreprise » sur cette seule ligne.

## Ce qui est collecté (lecture seule)

Toutes les requêtes portent le User-Agent `Mozilla/5.0 (compatible; ClientsIci-audit; +https://clientsici.fr/)`. Budget : 8 requêtes HTML au maximum par site (compteur dans `meta.requetes_html`), plus `robots.txt` et jusqu'à 3 candidats de sitemap, plus les ressources que le navigateur charge lui-même. Corps HTML lu jusqu'à 3 Mo. Aucun formulaire soumis, aucun espace d'administration visité, aucun annuaire tiers interrogé.

| Étape | Détail | Requêtes |
|---|---|---|
| Accueil | GET de l'URL donnée avec suivi des redirections (chaîne conservée), en-têtes (HSTS, Server) | 1 HTML |
| Redirections | si l'URL finale est en https : test de `http://hôte/` ; sinon test de `https://hôte/` (pour distinguer « pas de HTTPS » de « HTTPS non forcé ») ; test de la variante avec/sans `www` | 2 HTML (sans lecture du corps) |
| Pages internes | liens de même hôte trouvés sur l'accueil, classés par mots-clés (contact, devis, services/prestations, à propos, réalisations, tarifs, horaires) avec bonus pour les liens du menu ; une page par catégorie puis les meilleures restantes ; repli sur les liens du menu (`navigation`) ; exclusion des fichiers (.pdf, .txt, .xml…) et des pages légales | jusqu'à 4 HTML |
| robots.txt | existence, `Disallow: /` pour `User-agent: *`, directives `Sitemap` | 1 |
| Sitemap | candidats : ceux du robots.txt puis `/sitemap.xml`, `/sitemap_index.xml` ; type (`urlset` ou `index`), nombre de `<loc>` ; aucune exploration des sous-sitemaps | 1 à 3 |

Pour chaque page HTML : status, title (longueur), meta description (longueur), H1 (liste et nombre), H2/H3, meta viewport, lang, canonical, meta robots, meta generator, nombre de liens internes/externes, liens `tel:`/`mailto:`, images sans alt (nombre, exemples), scripts externes (domaines), générateur détecté par traces (WordPress, Wix, Jimdo, Weebly, SITE123, Webself, e-monsite, Google Sites, Wifeo, SiteW, Webnode, IONOS, GoDaddy, Simplébo, Solocal, Duda, Webflow, Squarespace, Shopify, PrestaShop, Joomla, Drupal…) avec marquage « gratuit / grand public », types JSON-LD (récursif, `@graph` compris) et présence d'un type LocalBusiness ou dérivé, téléphones et e-mails par regex (numéros français normalisés), adresses par heuristique (code postal à 5 chiffres + ville, rue si elle précède), mentions « devis » et « urgence », année de copyright, départements/régions cités et formules de zone d'intervention (« intervient à… », « km autour », « et ses environs »…).

Navigateur (Playwright Chromium headless, même User-Agent, locale fr-FR) sur l'accueil, en 375×812 (mobile, DPR 2, tactile) puis 1440×900 : status, temps jusqu'à `networkidle` (30 s maximum, sinon « non atteint » et analyse en l'état), nombre de requêtes et octets transférés (CDP `Network.loadingFinished`, octets encodés), erreurs console et exceptions JS, `scrollWidth` contre `innerWidth` (débordement), boutons d'appel et de contact visibles (`metriques.appels`, 20 au plus, les visibles sans défiler d'abord : liens `tel:`, liens de messagerie `mailto:`/`sms:`/WhatsApp, éléments `a`/`button`/`[role=button]` dont le texte, l'`aria-label`/`title`, la classe ou l'id contient rdv, rendez, contact, appel, téléphone, phone, tel, devis, joindre, rappel, ou dont le lien mène à une page contact/rendez-vous/devis), chacun avec position par rapport au premier écran, `fixe` (position `fixed`/`sticky` sur l'élément ou un ancêtre) et `motif` de détection ; synthèse dans `metriques.bouton_contact` (`tel_visible_sans_defiler`, `contact_visible_sans_defiler`, `fixe_visible_sans_defiler`, `tel_present`), plus petit texte visible (taille calculée, exemple, nombre d'éléments sous 12 px, 4 000 éléments examinés au plus), captures `captures/mobile-375-fold.png`, `mobile-375-full.png`, `desktop-1440-fold.png`, `desktop-1440-full.png` (pleine page tronquée à 12 000 px sur les très longues pages).

Lighthouse 12 (`npx -y lighthouse@12`, émulation mobile, throttling simulé, catégories performance/accessibilité/bonnes pratiques/SEO, 180 s maximum) : scores sur 100, LCP, CLS, TBT, FCP, Speed Index, poids total ; rapport brut dans `lighthouse.json`. En cas d'échec ou de `runtimeError`, statut « non mesuré » avec la raison.

## Analyse : constats, verdict, points positifs

Chaque constat : `{id, type (fait observé | mesure), gravite (haute | moyenne | basse), titre, preuve {url, valeur}, consequence_possible, correction}`. Règles appliquées :

| Gravité | Règle |
|---|---|
| haute | site servi sans HTTPS ; redirection http→https absente (y compris « HTTPS disponible mais non forcé ») ; meta viewport absente ; débordement horizontal à 375 px ; performance Lighthouse < 50 ; accueil `noindex` ; `robots.txt` bloquant tout ; page d'accueil non chargée |
| moyenne | performance Lighthouse 50–79 ; title absent, trop long (> 65) ou dupliqué entre pages ; meta description absente ; aucun lien `tel:` sur les pages consultées ; « Aucun bouton de contact visible sans défiler à 375 px » (lien `tel:` présent plus bas, mais ni lien d'appel ni bouton de contact sur le premier écran mobile) ; aucune ville/zone repérée sur l'accueil ; canonical vers un autre domaine ; lien de menu vers une page en erreur ; accueil > 3 Mo sur mobile |
| basse | « Bouton de contact visible sans défiler à 375 px, mais sans lien d'appel direct » (bouton fixe ou non, repéré par son texte, son aria-label, sa classe ou son lien vers une page contact, sans `tel:`) ; H1 absent ou multiple ; images sans alt ; JSON-LD LocalBusiness absent ; copyright ancien (« indice de site non mis à jour ») ; générateur grand public (information) ; `lang` absent ; description > 165 ; textes < 12 px (≥ 3 éléments) ; erreurs console ; mot « devis » absent ; versions www et sans www toutes deux servies ; score Lighthouse accessibilité/SEO/bonnes pratiques < 70 |

Bouton d'appel sur le premier écran mobile (navigateur requis, sinon rien n'est compté) : trois cas distingués. (1) un lien `tel:` cliquable est visible sans défiler → point positif ; (2) un bouton ou lien de contact est visible sans défiler mais sans lien d'appel direct → constat basse, formulé « Bouton de contact visible sans défiler à 375 px, mais sans lien d'appel direct » (la formulation ne dit jamais « non visible » quand un bouton de contact est visible) ; (3) ni lien d'appel ni bouton de contact sur le premier écran → constat moyen « Aucun bouton de contact visible sans défiler à 375 px » si un lien `tel:` existe plus bas ; s'il n'y a aucun lien `tel:` sur le site, seul le constat moyen « Aucun numéro de téléphone cliquable » est émis, avec la mention « aucun bouton de contact visible sans défiler » dans sa preuve (pas de double constat). Les conséquences possibles sont rédigées au conditionnel (« peut », « risque de ») ; la correction des images sans alt donne un exemple fondé sur `--metier` (et `--ville`) s'ils sont transmis, sinon une consigne générique sans exemple ; les ressources en échec sont désignées « ressources en erreur (4xx) ».

Ce qui n'a pas pu être testé (http en délai dépassé, navigateur en échec, Lighthouse en erreur) n'est jamais compté comme constat : il va dans `analyse.non_verifie` et apparaît dans le rapport comme « non vérifié » / « non mesuré ».

Verdict : « refonte pertinente » si ≥ 2 constats hauts ou 1 haut + 2 moyens ; « amélioration ciblée préférable » si ≥ 2 moyens sans haut ; « informations insuffisantes » si l'accueil n'a pas pu être chargé ou s'il y a moins de 3 constats ; sinon « aucune amélioration substantielle établie ». Le motif chiffré est conservé (`verdict_motif`).

`ce_qui_fonctionne` : liste des points positifs établis (HTTPS + redirection, HSTS, viewport, pas de débordement, scores Lighthouse ≥ 80/90, title et description présents, H1 unique, tel: présent et visible, ville visible, LocalBusiness, alt complets, copyright à jour, sitemap, robots). `a_preserver` : pages trouvées (rôle, URL, title, status), libellés du menu, coordonnées relevées (téléphones, e-mails, adresses ; un numéro n'est retenu que si son séparateur est le même entre tous les groupes, ce qui écarte les dates du type « 2026-09-15 15:35:05 »), `services_listes` (« à vérifier », 12 entrées dédoublonnées au plus) : d'abord les listes de prestations (`ul`/`ol` qui suit un H2/H3 contenant prestation, service, nos métiers, savoir-faire, spécialités, domaines d'intervention…), puis les titres H2/H3 des pages services puis accueil, hors `<form>`, lignes des titres multi-lignes (`<br>`) jointes par un espace, en excluant les titres finissant par « , », « ? », « : », les sections génériques (« Nos solutions », « Réalisations »…), les appels à l'action et questions (« Demander… », « Obtenez… », « Pourquoi… », « Comment… »), les titres de plus de 6 mots, les slogans tout en majuscules, et les pages actualités/recrutement/emploi/carrière/mentions (jamais classées « services » lors du choix des pages internes). `analyse.correspondance_entreprise` : voir plus haut.

## Sorties dans `--out`

- `audit.json` : tout (meta et paramètres, cible et chaîne de redirections, tests http/https/www, pages, robots, sitemap, navigateur, lighthouse, analyse, erreurs, journal des requêtes avec durée et status).
- `audit.md` : synthèse (5 lignes au plus), ce qui fonctionne, actions prioritaires (8 au plus), tableau priorité / problème / preuve / conséquence / correction, « non vérifié », mesures et conditions (outil, date, URL, conditions pour chaque mesure), pages consultées, risques de refonte et éléments à préserver, verdict motivé avec rappel de la règle et des limites.
- `captures/*.png` : quatre captures (fold et pleine page, mobile et desktop).
- `lighthouse.json` : rapport brut Lighthouse (absent si non mesuré).

## Limites connues

- Lighthouse est une mesure unique, simulée, depuis un serveur : sur un gros site la performance a varié de 46 à 67 en cinq minutes. Avant d'écrire un chiffre de vitesse dans un e-mail, refaire une mesure (ou deux) et citer la fourchette, conformément à la consigne « mesurées avec un outil, pas estimées » de la page `/refonte-site-vitrine/`.
- Détections de ville, d'adresse, de téléphone et de services : heuristiques par regex, listes et titres H2/H3, à relire (le rapport le dit). L'option `--ville/--cp` avec la commune du lead rend le test « ville sur l'accueil » fiable ; `--nom/--enseigne/--siren` alimentent `correspondance_entreprise`.
- Bouton de contact : la détection repose sur le texte, l'aria-label, la classe/id et le lien de l'élément ; un bouton purement graphique sans aucun de ces indices n'est pas vu (le constat moyen peut alors être à nuancer à l'œil sur `captures/mobile-375-fold.png`). Un élément masqué par un bandeau cookies reste compté comme visible.
- Un site qui bloque les robots (WAF, captcha, 403 sur User-Agent inconnu) donnera « informations insuffisantes » ; le script n'essaie pas de contourner.
- Les sites rendus uniquement en JavaScript sont analysés côté `requests` sur le HTML brut (title, liens, texte peuvent manquer) ; le navigateur, lui, voit la page rendue, mais seuls le débordement, les boutons d'appel, les tailles de texte et les métriques réseau en sont tirés.
- Le test `http://` peut être en délai dépassé derrière certains pare-feu (cas service-public) : marqué « non vérifié », jamais compté.
- Pas de vérification de la cohérence avec la fiche Google (hors périmètre, pas de Google Maps) ni des formulaires (aucune soumission).
- La règle « aucune mention devis » est pensée pour les artisans ; sur un commerce elle peut être à ignorer (gravité basse, sans effet sur le verdict).
- Durée : 15 à 30 s pour un petit site, jusqu'à 90 s pour un site lourd (délais HTTP + networkidle + Lighthouse). Pour un lot de leads, prévoir une exécution séquentielle (Lighthouse en parallèle fausse les mesures).

## Enchaînement avec les autres composants

- Entrée : l'URL `site_web` d'un lead (composant A, `scripts/leads-france`) et, si disponibles, sa commune et son code postal (`--ville`, `--cp`), sa dénomination, son enseigne et son SIREN (`--nom`, `--enseigne`, `--siren`), le libellé de son métier (`--metier`).
- Tests hors ligne : `scripts/test_audit_site.py` (unittest, aucune requête réseau ; un test Playwright sur une page locale avec un bouton fixe). Les titres de constats sont des motifs pour `templates/email_phrases.json` (catégories `appel_fold`, `contact_sans_appel`, `tel`…) : tout nouveau titre doit y être ajouté.
- Sorties réutilisables : `analyse.constats` (preuves prêtes à citer dans l'e-mail : un seul point précis, comme la page `/refonte-site-vitrine/` le promet), `analyse.ce_qui_fonctionne` et `analyse.a_preserver` (textes, coordonnées, pages à reprendre dans la maquette et à rediriger), `captures/` (pièces jointes de l'audit écrit), `verdict` (filtre : n'écrire qu'aux prospects en « refonte pertinente » ou « amélioration ciblée préférable »).
